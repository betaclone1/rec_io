# Architecture overview

High-level view of the REC.IO trading system: components, data flow, and where things live. For runbooks and schema details, see [docs/README.md](README.md).

## Components

| Layer | Purpose |
|-------|---------|
| **Backend** (`backend/`) | Python services: FastAPI main app, trade manager, trade executor, per-monitor supervisors, watchdogs (Kalshi, price, strike tables), account sync, health monitors. All use a single DB config and port manifest. |
| **Frontend** (`frontend/`) | Web UI: dashboard, trade monitor, history, settings, account manager, system tab. Served by main_app; talks to backend via API and websockets. Tabs are loaded on first view (desktop and mobile); do not assume all iframes are loaded on DOMContentLoaded. |
| **Scripts** (`scripts/`) | DB migrations and drift check (`db/`), config generation (`config/`), backup (`backup/`), monitor/user management (`manage/`), install and deploy (`install_deploy/`). Run from repo root with PYTHONPATH or env as needed. |
| **PostgreSQL** | Single database: schemas `users`, `live_data`, `system`. Trades, monitors, account history, strike tables, price logs, schema_migrations. Config via `DB_*` or `REC_DB_*` (see [backend/core/config/database.py](../backend/core/config/database.py)). |
| **Redis** | Real-time backbone: one channel `rec_io:db_changes` for all DB-driven events. Switchboard publishes here; frontend (WebSocket) and backend (Redis subscribe) consume the same payload. See [REALTIME_BACKBONE.md](REALTIME_BACKBONE.md). |
| **Switchboard** | Single process: LISTENs to PostgreSQL NOTIFY, maps (schema, table) → stream name via [backend/core/stream_registry.py](../backend/core/stream_registry.py), publishes to Redis, serves `/ws/db_changes`. Run under supervisor; port 3010 by default. |
| **read_api** | Single persistent process (supervisor: `read_api`). Hosts **all** read/aggregate HTTP endpoints (e.g. `/api/performance/realized`, `/api/account/balance`, `/api/subaccounts`, monitor stats, portfolio history). Request in → run query, compute, format → return JSON. Does not subscribe to Redis. See [REDIS_ARCHITECTURE.md](REDIS_ARCHITECTURE.md). |
| **Kalshi** | External: markets, order execution, account/fills/orders. Backend uses Kalshi API and websockets; credentials in env or `backend/data/users/.../credentials/`. |

## Data flow (simplified)

- **Market data:** Kalshi → kalshi_market_watchdog / live orderbook → `live_data` and strike tables. Price watchdogs → `live_data` price history.
- **Trading:** User/monitor config in `users.monitor_list_0001` → auto_entry_supervisor (entry logic) → trade_manager (lifecycle) → trade_executor (Kalshi orders). Fills/positions synced back via kalshi_account_sync.
- **Frontend:** Browser → main_app (port 3000) → API and websockets; main_app reads/writes DB and calls trade_manager/trade_executor where needed.
- **Real-time:** Any write to a watched table → trigger → NOTIFY → switchboard LISTEN → Redis → WebSocket (frontend). Frontend refetches **read_api** when it receives a stream change; read_api runs queries and returns JSON. No broadcast from main. See [REDIS_ARCHITECTURE.md](REDIS_ARCHITECTURE.md) and [REALTIME_BACKBONE.md](REALTIME_BACKBONE.md).
- **Config:** Env (`.env`, `DB_*` / `REC_DB_*`) → database.py and unified_config. Ports from `backend/core/config/MASTER_PORT_MANIFEST.json`. Supervisor config generated by `scripts/config/generate_unified_supervisor_config.py`.

## Process model

- **Supervisor** (`backend/supervisord.conf`) runs all backend processes. Config is generated so each program gets the right port and env.
- **MASTER_RESTART** (`scripts/MASTER_RESTART.sh`) flushes ports, regenerates supervisor config, and starts supervisor. Use this for a full restart after code or config changes.
- Per-monitor processes (auto_entry_supervisor, active_trade_supervisor) are spawned by monitor_manager; ports assigned from the manifest.
