# Changelog

This folder holds:

- **MASTER_CHANGELOG.md** — Single internal changelog for production deployments.
- **CHANGELOG_AGENT_INSTRUCTIONS.md** — Instructions for the production agent (or `/apply-update` action): read all open entries, execute each checklist fully, and update checkboxes. Use this when running the changelog workflow.
- **TODO.md** — Pointer to task tracking: active backlog is in `.cursor/plans/`. Historical changelog backlog was archived to `archive/2026-03-housekeeping/docs/TODO_changelog_backlog.md`; we work from the PM system (plans) from here on.

- **When to update:** Add a new timestamped entry whenever you are about to push an update to production (e.g. after merging a feature branch to `main`).
- **What to include:** Summary of the change plus a **Production checklist**: markdown checkboxes (`- [ ]`) for every task to complete when applying the update (from local via /apply-update-from-local or on prod via /apply-update). **Release:** each new entry must include **`Release: vNEXT`** in the Summary and a **`record_system_version.py --version NEXT`** checklist line (same version as git / prepare-update). Always include at least minimal items (e.g. "Confirm codebase changes"). **Migrations:** if the commit adds `scripts/migrations/*.up.sql`, each id **must** have `- [ ] Apply migration: … run_migration.py up <id>` (git files do not alter Postgres). Prefer that over vague “update local database” / `init_database()` on existing catalogs. The agent both completes the tasks **and updates the checklist in `MASTER_CHANGELOG.md`** by checking off each box (`- [x]`) when done.
- **Workflow:** Merge to `main` → on production **pull → apply listed migrations → restart** via **/apply-update-from-local** or **/apply-update** (checklist + orphan scan vs `run_migration.py list`). `/simple-pull` / `/remote-deploy` must **not** be used when the range includes new migration files. After any prod-only adjustments, run **/confirm-update**. An update is not finished until checklist items are `[x]` and required migrations appear in prod `system.schema_migrations`. Law: `.cursor/rules/10-deploy-migrations-gate.mdc`.
- **Confirm-update:** Run on prod after apply-update (and any tweaks). Reviews git changes, MASTER_CHANGELOG checkboxes, and notes (e.g. `.cursor/plans/`, optional `docs/changelog/CONFIRM_UPDATE_NOTES.md`). Produces a confirmation summary and ensures the repo is ready to push so dev can pull and stay identical.
- **Running Python scripts:** Use the project venv so dependencies (e.g. `cryptography`) match the rest of the stack. From project root: `PYTHONPATH=$(pwd) venv/bin/python path/to/script.py` — not bare `python3`, which may point to a different environment and cause failures (e.g. missing `PSS.DIGEST_LENGTH` in Kalshi signing).
